# Метазапрос для генерации CLI Prompt

Сформулируй один CLI prompt **на английском языке** для Qwen3-Coder-Next.

Актуальное состояние реального репозитория содержится в приложенном repository snapshot `semcat_NN.md`.

CLI prompt должен охватывать только выбранную подзадачу:

```text
<НАЗВАНИЕ ВЫБРАННОЙ ПОДЗАДАЧИ>
```

В ответе выведи **только готовый CLI prompt на английском языке**. Не добавляй русский вводный текст, объяснение, комментарий, анализ или любой иной текст вне prompt.

---

## Назначение и границы

Сформулируй точный implementation prompt для реального Python-репозитория семантической категоризации VepKar. В репозитории есть Python CLI-модули, pandas-преобразования, CSV data contracts, офлайн pytest-тесты и необязательные runtime-компоненты для моделей и лингвистических ресурсов.

Каждый сгенерированный CLI prompt выполняется coding agent в **новой независимой сессии VS Code / Kilo Code**. Поэтому prompt должен быть самодостаточным:

- описывай только текущую выбранную подзадачу и нужный для неё локальный контекст;
- не ссылайся на текущую беседу, repository snapshot, предыдущие или следующие группы работ, «уже сделанные шаги» либо будущие миграции;
- не предлагай agent читать приложенные файлы или историю: он должен читать реальные файлы репозитория, необходимые для текущей задачи;
- не требуй реализации соседней работы «заодно».

Если в коде обнаружена проблема вне scope, agent не должен исправлять её попутно. Он должен оставить её без изменений и кратко указать в `Known limitations`, только если она мешает или существенно влияет на выбранную задачу.

---

## Пути, scope и изменения

В CLI prompt требуй:

- использовать только реальные текущие пути, имена модулей и имена полей, проверенные в репозитории;
- указывать каждый файл полным относительным путём от корня репозитория;
- до требований к реализации перечислять точные in-scope файлы;
- не менять несвязанные модули, зависимости, lock-файлы, конфигурацию, настройки тестов и README, если это не является прямой необходимостью выбранной задачи;
- объяснять в финальном отчёте необходимость любого изменённого файла вне первоначального scope;
- удалять мёртвый код, legacy compatibility и тесты только тогда, когда выбранная подзадача устраняет их последний реальный production-потребитель.

Не придумывай пути, API, существующие поля, тесты или соглашения репозитория. Не переименовывай файлы и модули только ради стиля.

## Data contracts и семантика

Рассматривай CSV schemas и значения DataFrame как публичные data contracts.

Если выбранная подзадача затрагивает чтение, запись, преобразование или объединение CSV, prompt должен явно установить только применимые требования:

- точные затронутые input и output files;
- условия создания output: всегда либо только при непустых данных;
- семантику включаемых и исключаемых строк;
- обязательные столбцы и их порядок, если меняется schema;
- правила для пустых, null и производных значений;
- составной ключ, правила уникальности и тип join, если они существенны;
- поля, которые намеренно не должны быть публичными.

Не считай schema корректной лишь потому, что writer или helper достроил отсутствующие колонки пустыми значениями. Производные значения и групповые статистики должны вычисляться там, где доступны все необходимые исходные и групповые данные; writer должен только сериализовать уже корректный результат.

Если изменяется взаимоисключающая классификация, требуй подходящий проверяемый conservation invariant: каждая исходная строка должна попасть ровно в один предусмотренный класс либо быть явно исключена по документированному правилу.

Сохраняй различие между исходными полями и реально существующими нормализованными или производными полями. Не предписывай широкое терминологическое переименование, если оно не входит в scope.

При необходимости учитывать утверждённое направление текущего проекта:

- единица перевода и семантической обработки — полное словарное значение;
- содержательные поля называются `pos`, `meaning_ru`, `meaning_en` и, для QA, `meaning_ru_back`;
- идентичность задаётся составной парой `("pos", "meaning_ru")`;
- не вводи сериализованный дублирующий идентификатор вроде `task_key`, если пара полей уже присутствует;
- объединения и дедупликация используют составной ключ, когда это входит в задачу;
- не сохраняй и не возрождай legacy-терминологию коротких глосс, если это не требуется явно выбранной задачей.

## Требования к реализации

Сформулируй небольшие, упорядоченные и проверяемые требования. Включай кодовые фрагменты лишь тогда, когда они предотвращают существенную неоднозначность в критической логике, например в pandas merge, группировке, validation или обработке schema.

Фрагмент должен быть локальным и минимально достаточным. Не вставляй большие шаблоны, полные исходные файлы или частные примеры, не нужные для выбранной задачи. Не предписывай точный код, если agent сначала должен установить локальные соглашения, прочитав in-scope файл.

Не добавляй silent fallback, который меняет научную или data semantics. При невалидном input contract предпочитай ясную validation error; предупреждение допустимо только там, где дальнейшая работа остаётся семантически корректной.

Не добавляй broad silent exception handling, не ослабляй assertions, не отключай тесты и не меняй dependency/runtime configuration, если это не входит в задачу.

Backwards compatibility и автоматическую миграцию старых артефактов требуй только при прямом требовании выбранной подзадачи. Для несовместимого data contract предпочитай явный отказ с полезным сообщением, а не неявное переименование столбцов.

## Тестирование и валидация

Если задача меняет воспроизводимое поведение, CLI, преобразование DataFrame, schema, persistence, классификацию или data semantics, требуй focused tests.

Тесты должны быть:

- расположены по реальным полным путям, обычно в `tests/sem_cat/`;
- офлайн, детерминированными и быстрыми;
- основаны на маленьких synthetic DataFrame и `tmp_path`, когда затрагиваются файлы;
- независимы от реальных экспортов ВепКар, LLM, загрузки Hugging Face, GPU/CUDA, NLTK download, proxy и сети;
- ориентированы на наблюдаемое поведение и содержание результата, а не только на существование импорта, функции или класса.

Для исправляемой ошибки требуй regression test, который был бы красным до исправления.

Для записи CSV требуй, когда применимо:

- проверку репрезентативного непустого output;
- проверку пустого output со стабильным header, если такой файл обязан создаваться;
- проверку строк, включённых и исключённых по правилам;
- точных required columns и их порядка, если это относится к задаче;
- важных вычисленных значений, уникальности, join cardinality и отсутствия запрещённых публичных полей.

Если legacy-функция, тест или fixture больше не имеет production-потребителя вследствие выбранной задачи, требуй удалить его и удалить/переписать исключительно обслуживающие его тесты. Не удаляй тест, который по-прежнему защищает актуальное поведение под новым API.

Agent обязан запускать весь релевантный focused test file или directory, а не только новые test functions. Если нерелевантный тест падает из-за необязательной локальной зависимости, он должен сообщить точную команду, тест и краткую root cause; не следует скрывать проблему через skip, xfail, ослабление assertion или изменение test discovery.

Определи наблюдаемые completion criteria для выбранной задачи. При необходимости включи реальные output files, CLI behavior, headers, representative rows, границы классификации, invariants и результаты focused tests.

Если это возможно без запуска LLM или изменения обычных артефактов, добавь одну безопасную ручную validation command с temporary output directory.

## Требуемая структура CLI prompt

Сформируй prompt со следующими разделами, опуская раздел только если он заведомо неприменим:

1. `TOOL-CALL DISCIPLINE`
2. `TASK`
3. `SCOPE`
4. `CURRENT PROBLEM`
5. `REQUIRED IMPLEMENTATION`
6. `TESTS`
7. `OBSERVABLE COMPLETION CRITERIA`
8. `VALIDATION COMMANDS`
9. `FINAL REPORT`

В разделе `TOOL-CALL DISCIPLINE` требуй использовать доступный нативный structured editor/tool interface, предварительно читать точный изменяемый фрагмент и выполнять небольшие атомарные изменения. Agent должен следовать фактической schema доступного инструмента, а не угадывать имена его параметров и не печатать псевдо-tool calls вместо выполнения действий.

В разделе `FINAL REPORT` потребуй ровно такие подразделы:

- `Changed files`
- `Implemented requirements`
- `Tests run`
- `Known limitations`

---

## Ограничение final report

Потребуй краткий final report объёмом не более 900 токенов.

- `Changed files`: только реально изменённые полные относительные пути; объяснить необходимый выход за scope.
- `Implemented requirements`: от 3 до 8 коротких пунктов о наблюдаемом реализованном поведении и важных schema/API изменениях.
- `Tests run`: точные запущенные команды и только итог каждой команды: passed/failed/skipped counts.
- `Known limitations`: только незавершённость, failure, отклонение от scope или существенное ограничение; для failure — точный test/command и краткая причина.

Не пересказывай prompt, не показывай ход размышлений, промежуточные tool calls или полные изменённые фрагменты кода. Не объявляй задачу завершённой, если релевантные tests не прошли.
